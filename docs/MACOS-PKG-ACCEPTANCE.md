## Build on each native architecture

The tmux builder runs its output, so use a native arm64 Mac for arm64 and an
Intel Mac for x64. These are **separate packages**, not universal binaries.
The repository has both build paths; neither new candidate has been built or
accepted on a Mac by this Linux implementation task. macOS 13.0 is tmux's
configured deployment target, not evidence that the entire product works on
every macOS version. Test the intended minimum OS separately.

Use a separate checkout/worktree of the feature branch on the Mac. A build
host needs Xcode Command Line Tools, Git and network access. End users on the
prebuilt PKG path should need neither CLT nor Homebrew.

Build the pi-web artifact using an isolated directory (no service stage):

```bash
case "$(uname -m)" in
  arm64) ARCH=arm64 ;;
  x86_64) ARCH=x64 ;;
  *) exit 1 ;;
esac
BUILD_HOME="$(mktemp -d "$HOME/pi-agent-pkg-build.XXXXXX")"
PI_AGENT_HOME="$BUILD_HOME" ./install.sh node fetch piweb
PI_AGENT_HOME="$BUILD_HOME" scripts/build-piweb-artifact.sh "$PWD/dist"
scripts/build-macos-tmux.sh "$PWD/dist/tools-macos-$ARCH"
bash tests/build-macos-pkg.sh
```

The pi-web filename uses **PIN_PI_WEB_VERSION**, not the candidate PKG version.
Obtain the exact filename and SHA from `dist/piweb-*-macos-$ARCH.tar.gz.sha256`.
No public staging or release is required. Choose one of the two sources below.
`PI_AGENT_VERSION` overrides both the package filename/component version and the
staged payload `VERSION`. Supported syntax is SemVer core plus optional prerelease
(no build metadata); the builder reads the version back through pkgutil expansion
and PackageInfo XML, and fails if Apple's tools do not preserve it exactly.

### Local embedded artifact (Intel candidate; also supported for arm64)

Use the exact tarball generated by that architecture's build. This example is for
Intel; it does not upload anything:

```bash
ARTIFACT_FILE="$PWD/dist/piweb-0.10.0-macos-x64.tar.gz"
ARTIFACT_SHA256="$(awk '{print $1}' "$ARTIFACT_FILE.sha256")"
PI_AGENT_VERSION=0.3.0-rc.8 scripts/build-macos-pkg.sh \
  --artifact-file "$ARTIFACT_FILE" --artifact-sha256 "$ARTIFACT_SHA256" \
  --arch x64 --tools "$PWD/dist/tools-macos-x64" --out "$PWD/dist/private-unsigned"
```

`--artifact-file` and `--artifact-url` are mutually exclusive. SHA is mandatory in
both modes. File mode requires the basename `piweb-<version>-macos-<arm64|x64>.tar.gz`;
`--arch` asserts the requested target (otherwise derived from the filename), and
tmux must match it. Invalid names/target mismatch fail before copying. These are
filename and tmux architecture checks, not proof of every module inside a renamed
archive; use the native build for the target and run its runtime acceptance.

The builder verifies SHA before and after copying, then after native package
expansion. The per-user helper verifies the embedded archive's filename against
`uname -m`, rejects symlinks, and checks SHA again **before calling install.sh**.
This is required because install.sh's local-file branch does not check a digest.
A mismatch fails setup without running the installer. The tarball stays under
`/usr/local/lib/woow-pi-agent/artifacts/`; switching source modes overwrites both
source manifests so stale URL/file selectors cannot win.

This makes **pi-web** self-contained, not the entire installer: Node, plugins,
CLIs and Python dependencies still need internet. The archive contains native
modules. Apple's real notarization of the unsigned embedded arm64 tree failed:
submission `c19875c2-1737-493b-b096-ec805e5e7cf9`, status **Invalid**, reported
libvips/sharp/next-swc missing Developer ID signatures and secure timestamps.
The package's own signature and signed tmux do not fix unsigned nested binaries.
**Use the signing step below before an embedded formal build.** The release
builder now verifies every embedded native file before package building/signing
or submitting to Apple. It does not silently sign or replace the supplied SHA.

### Sign an embedded pi-web artifact (build host only, Python 3.9.6 compatible)

Use a dedicated build directory with enough room for the input snapshot, expanded
runtime and new tarball. The helper needs Apple's `codesign`, `lipo`, `file`,
Python 3.9+ and network access for secure timestamps. It does not install Python,
import certificates or unlock keychains. `/usr/bin/python3` from CLT 3.9.6 is
supported; the wrapper runs it with `-I`. An existing managed interpreter can be
selected with `PI_AGENT_BUILD_PYTHON=/absolute/path/to/python3`. End-user setup
never runs this helper and does not gain a Python/CLT requirement.

```bash
ARCH=arm64  # use x64 for the native Intel build
INPUT="$PWD/dist/piweb-0.10.0-macos-$ARCH.tar.gz"
INPUT_SHA="$(awk '{print $1}' "$INPUT.sha256")"
SIGNED="$PWD/dist/piweb-0.10.0-signed-macos-$ARCH.tar.gz"
: "${SIGN_APP:?existing Developer ID Application: Name (TEAMID)}"
PI_AGENT_BUILD_PYTHON=/usr/bin/python3 scripts/sign-macos-piweb-artifact.sh \
  --artifact-file "$INPUT" --artifact-sha256 "$INPUT_SHA" \
  --out "$SIGNED" --sign-app "$SIGN_APP"
# Add --keychain "$SIGNING_KEYCHAIN" only for an existing non-default keychain.
# Equivalent direct interpreter invocation:
# /usr/bin/python3 -I scripts/macos/piweb-artifact-signing.py <same arguments>
SIGNED_SHA="$(awk '{print $1}' "$SIGNED.sha256")"
scripts/sign-macos-piweb-artifact.sh --verify-only \
  --artifact-file "$SIGNED" --artifact-sha256 "$SIGNED_SHA" --sign-app "$SIGN_APP"
```

The source archive remains unchanged. The helper creates a private snapshot,
verifies its explicit SHA before unpacking, and rejects absolute/traversal paths,
duplicate entries, special files, escaping link targets and writes through links.
It retains source content (including `.git/HEAD`, refs, package and lock files)
and internal relative symlinks. AppleDouble `._*` / `__MACOSX` bookkeeping and
archive xattrs/ownership are not carried forward; stale resource-fork metadata
must not be restored over freshly signed binaries. Hardlink members are safely
materialized as separate regular files.

All regular files are scanned by Mach-O magic and `file` classification, including
files without extensions or executable bits, executables such as esbuild when
present, dylibs and `.node` files. Every Mach-O is signed with Developer ID
Application, `--options runtime --timestamp`, then checked with strict
all-architecture verification. `lipo` enumerates every slice; each slice must
show the expected Developer ID authority, runtime flag and secure timestamp.
Included prebuilds for other architectures are signed too. No `--deep` shortcut
or fixed filename allowlist is used. No entitlements are added. These signing
options follow [Apple’s distribution-signing guidance](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac).

If `--keychain` is supplied, commands run under the account's real HOME and the
existing keychain is temporarily added to the user search list; the exact list
(including paths with spaces) is restored in `finally` on success or command
failure. The build lane should still treat forced process termination as an
interruption requiring a check of its keychain search list.

Outputs are a **new** architecture-named tarball, `.sha256`, and `.signing.json`
with input/output hashes, public signing identity and the complete native file
inventory. Existing outputs are refused. The report asserts that all non-native
file bytes/modes and symlink targets stayed unchanged. Never reuse INPUT_SHA for
the signed output: signing and repacking necessarily produce a new digest.
No key material or keychain contents are written to the report or repository.

For formal embedded builds, substitute these parameters into the signing command
below:

```bash
# Keep all the --release / --sign-app / --sign / --notary-* options below.
# Replace its source arguments with:
# --artifact-file "$SIGNED" --artifact-sha256 "$SIGNED_SHA" --arch "$ARCH"
```

The builder's read-only preflight fails on unsigned/ad-hoc native objects,
missing runtime/timestamp, invalid strict signatures or unexpected Developer ID.
It verifies the caller's explicit digest and never alters it. Successful local
checks do not replace Apple's accepted notarization, staple validation or actual
Mac runtime tests. The signed artifact is a private candidate until those pass.

## Formal build gate (authorized signing lane only)

No signing material was accessed by the Linux implementation task. The signing
lane supplies existing identities and notary parameters using its established
credential handling. These are parameters, not credentials to paste into a report:

```bash
: "${SIGN_APP:?Developer ID Application: Name (TEAMID)}"
: "${SIGN_INSTALLER:?Developer ID Installer: Name (TEAMID)}"
: "${NOTARY_KEY_FILE:?existing AuthKey file path}"
: "${NOTARY_KEY_ID:?existing key ID}"
: "${NOTARY_ISSUER:?issuer UUID}"
PI_AGENT_VERSION=0.3.0-rc.8 scripts/build-macos-pkg.sh --release \
  --artifact-url "$ARTIFACT_URL" --artifact-sha256 "$ARTIFACT_SHA256" \
  --tools "$PWD/dist/tools-macos-$ARCH" --out "$PWD/dist/private-signed" \
  --sign-app "$SIGN_APP" --sign "$SIGN_INSTALLER" \
  --notary-key "$NOTARY_KEY_FILE" --notary-key-id "$NOTARY_KEY_ID" \
  --notary-issuer "$NOTARY_ISSUER"
# Optional existing non-default signing keychain: add --keychain /path/to/keychain.
scripts/verify-macos-pkg.sh \
  "$PWD/dist/private-signed/WoowPiAgent-0.3.0-rc.8-macos-$ARCH.pkg"
```

For embedded mode, replace `--artifact-url "$ARTIFACT_URL"` above with
`--artifact-file "$ARTIFACT_FILE"`, and use that local artifact's SHA and target
tools. All signing and notarization parameters and gates are the same.

`--release` fails before build if either Developer ID identity or any notary
parameter is missing. In embedded mode it also rejects unsigned native files
before package construction or submitting to Apple. It then requires accepted
notarization and a valid staple.
The independent verifier checks package Installer identity, staple, Gatekeeper,
and bundled tmux's strict signature, Developer ID Application authority,
hardened runtime and timestamp. Nonzero means **do not hand off as releasable**;
a failed build may leave a diagnostic PKG on disk. This gate validates the PKG
and its bundled tmux; it does not establish native runtime behavior for either
an external or embedded pi-web tree. Record the
artifact SHA and runtime acceptance independently. A gate pass grants no public
release authorization.

## Launcher trust and stdin review

Distribute the **PKG**, not standalone `.command` downloads. Apple DTS explains
that Finder sends command-line tools to Terminal as documents, which can trigger
Gatekeeper's document path; installing via a Gatekeeper-approved installer package
is an explicitly documented remedy. See [Apple: Resolving Gatekeeper Problems](https://developer.apple.com/forums/thread/706379).
Package signing does not make a separately downloaded copy of our unsigned shell
entry independently trusted. Our supported path is browser-download signed PKG →
Installer → installed Applications entry. Native verification must retain normal
quarantine/Gatekeeper behavior and inspect `xattr -l` on both the downloaded PKG
and installed entries; no quarantine stripping is part of setup.

Postinstall does not start Terminal or call the `.command` wrapper. It calls the
helper with `--install`, which does not read stdin, open a browser, or wait for
Return. The only `read` is in the Finder wrapper's failure path. Linux fixture
checks exercise helper success/failure with stdin `/dev/null`. During Installer,
output goes to the installer wrapper log and per-user setup log; visible Terminal
progress begins only when the user opens an Applications entry. `launchctl asuser`
selects the GUI bootstrap context; it does not create a terminal/TTY. Actual login
Keychain accessibility and Finder file associations remain Mac acceptance items.
